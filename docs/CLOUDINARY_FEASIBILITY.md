## Prompt 24: authenticated ciphertext gateway

`GET /api/files/:id/access` and `GET /api/files/:id/download` now return only the encrypted `.dat` container, selected solely by a MongoDB file ID. Both routes pass the owner session, lock state, expiry/revocation checks, the default-deny proxy, and a server-side lookup that requires the current owner, `ready` lifecycle state, active folder ancestry, `raw/authenticated` delivery, an immutable provider asset ID and a correctly shaped v1 manifest. Invalid, foreign, deleting, missing and guessed IDs all receive the same `404` envelope after authorization. Locked, expired, revoked and anonymous sessions receive `401`; neither route permits Cloudinary public IDs, URLs or variants from a request.

The gateway creates a Cloudinary signed delivery URL only in server memory, sends Cloudinary one exact single-byte `Range` request, validates `206`, `Content-Range`, `Content-Length` and the readable body, and streams the response to the owner with `Cache-Control: private, no-store`, `Vary: Cookie`, `Referrer-Policy: no-referrer` and `X-Content-Type-Options: nosniff`. It supports explicit, open-ended and suffix byte ranges, returns `416` with `Content-Range: bytes */<stored-size>` for an owned unsatisfiable range, and cancels the provider reader if the browser disconnects. A missing Range header becomes the full known ciphertext range. The response does not expose a signed Cloudinary URL, a public ID, an asset ID, a filename, a key or plaintext bytes. There are no stored Cloudinary thumbnail or derived-variant objects in the current schema; any future variant needs the same file-owned authorization and gateway checks before it can be delivered.

The browser still receives ciphertext only. Prompt 24 does not add a preview, MediaSource player, plaintext download, thumbnail display or client decrypt-and-save flow. The existing crypto format decrypts and authenticates chunks locally after a later client fetcher supplies these bytes. It is therefore unsafe to describe ordinary `/download` navigation as a usable plaintext download yet. Keep original files until that client integration and the encrypted MP4 MediaSource design are implemented.

`npm run media:access-check` is a guarded live provider check. It creates one random locally encrypted synthetic object, confirms an unsigned Cloudinary URL is denied, confirms two server-signed proxy ranges return exact bytes, and destroys the object in `finally`. It does not log credentials, URLs, object IDs or bytes. The current Free account's 10 MiB raw cap continues to block the PRD's single-object near-100 MB video requirement. If this gateway's live range check stops returning exact `206` responses, encrypted seek streaming is **BLOCKED** until the storage design is reviewed.

## Prompt 23: bounded transfer and upload manager

The owner browser now optimizes images and supported videos locally, shows a local preview for approval, encrypts in v1 chunks, then sends **only ciphertext** to `PUT /api/uploads/[id]/ciphertext`. It separately encrypts the original user-facing name and the stored output name; the latter uses the actual output extension. Other supported and unknown files are encrypted unchanged as download-only metadata; PDF, ZIP/Office, RAR and UTF-8 text have local signature checks. Unknown binary files are marked `application/octet-stream` and must never be rendered inline. The ciphertext gateway exists, but local decryption and save/playback do not; do not delete originals. The UI shows queued, optimizing, review, encrypting, uploading, verifying, ready, failed and cancelled states. XHR reports browser-to-server transfer progress when measurable; Cloudinary and database verification remain indeterminate until completion.

The transfer route checks the owner session and same origin, enforces exact declared and received bytes strictly below 10,000,000, compares the first 80 ciphertext bytes with the reserved manifest, and uploads through the **server-only** Cloudinary SDK with the job's random `raw/authenticated` `.dat` ID and `overwrite:false`. It records the provider's immutable asset ID before the existing completion endpoint can mark a file ready. A failed or uncertain transfer leaves its opaque ID in the durable job for retry or reconciliation. Cancellation during a running transfer records a cancellation request and the transfer attempts remote cleanup before closing the job. Jobs are not ready merely because XHR reached 100%.

The 10,000,000-byte ceiling is conservative against the Free account's reported 10,485,760-byte raw cap and applies to every category on this transfer path. The PRD's image `<1,000,000` and video `<100,000,000` actual stored-object limits remain in effect. This design cannot store near-100 MB videos on the present plan. The browser makes a bounded ciphertext Blob to obtain real XHR upload progress; a larger plan requires a separately reviewed streaming or segmented transfer design. Pending job IDs and **encrypted** completion metadata live in tab session storage for refresh recovery. If transfer completed, the browser can retry completion; if the source selection was lost, the owner must cancel the old job and select the file again. The browser does not silently persist plaintext or ciphertext file blobs.

Synthetic tests cover encryption through a fake provider to one ready MongoDB-shaped record for image, video, document and other categories, exact byte checks, duplicate completion and local type classification. The existing image/video browser tests exercise their local optimizers separately. `npm run uploads:live-check` creates and deletes three small synthetic objects with the actual SDK adapter; on 2026-10-15 its upload, Admin lookup, signed range and cleanup passed for image, video and other ciphertext. The live API reported an **empty `format` field** for these raw `.dat` public IDs; verification now accepts that observed raw response while requiring the exact server-recorded `.dat` ID, `raw/authenticated` type, size, asset ID and version. A later run with an added anonymous-delivery request failed during its first upload, so that added check did not complete. The earlier independent Cloudinary probe confirmed anonymous HTTP 401 for small `raw/authenticated` objects. `npm run uploads:integration-check` subsequently passed for all three categories using disposable ciphertext objects and an isolated Atlas database; all objects and that database were removed. These synthetic category tests exercise storage contracts, not valid photo/video playback. Full browser-to-Atlas upload, mobile tests, authenticated download and true resumable large transfers remain unverified.

## Prompt 21 upload initiation decision

`POST /api/uploads/init` now accepts an owner-authorized, same-origin, strictly validated **v1 encrypted file manifest**. The intended sequence is local optimization, local encryption, then initiation; a manifest alone cannot prove those steps occurred. It checks the declared container layout and strict image/video ciphertext limit, confirms the vault ID and active folder, and reserves a pending MongoDB UploadJob in a transaction. The job inventories a random `vaultx/ciphertext/<opaque>.dat` Cloudinary ID with `raw/authenticated` delivery, a 10-minute intent expiry, and no-overwrite server upload options. It returns only the job/file IDs, declared bytes, expiry and `transferAvailable: false`. There is **no enabled ciphertext transfer, Cloudinary signature, file record or ready transition**. Pending reservations may remain in MongoDB after expiry until a later reconciliation worker is built; they do not create Cloudinary assets.

This is a deliberate security block, not a successful signed browser upload. Cloudinary's [signature rules](https://cloudinary.com/documentation/authentication_signatures) exclude `file` and the URL's `resource_type`, and signed signatures remain valid for one hour. Cloudinary's [upload preset rules](https://cloudinary.com/documentation/upload_presets) say signed request parameters override preset values and presets have **no per-preset file-size limit**. Therefore a signature handed to a browser does not itself bind the bytes, size, resource-type endpoint, or one-time use. A short VaultX job expiry cannot shorten Cloudinary's signature validity. Returning that capability would make the requested strict per-object limits and private raw destination unenforceable at initiation.

## Prompt 22 completion and orphan handling

`POST /api/uploads/complete`, `GET /api/uploads/[id]`, and `DELETE /api/uploads/[id]` now exist behind the owner session, lock state, no-store policy, and same-origin mutation check. Completion accepts an encrypted display-name envelope and allowlisted stored format/output metadata, but **no client Cloudinary ID, asset ID, or byte count**. It requires the immutable Cloudinary `asset_id` to have been recorded on the server-side UploadJob by a future ciphertext transfer. Since transfer is still disabled, normal init jobs cannot become ready. This is intentional.

For a job with a server-recorded asset ID, completion queries Cloudinary's [Admin resource API](https://cloudinary.com/documentation/admin_api) by that immutable ID, confirms the exact opaque `.dat` public ID, `raw/authenticated` mode, positive version and provider-reported stored ciphertext bytes. The raw API may return an empty `format` field, as observed in the live Prompt 23 check. Completion requires the actual bytes to equal the reserved v1 container size and to remain **strictly** below the PRD's decimal image/video cap. A bounded authenticated raw range request must return the exact reserved 80-byte ciphertext header with HTTP 206 and matching `Content-Range`. This binds the visible header to the stored object, but the header and encrypted metadata remain cryptographically authenticated **only when the owner browser decrypts them**. The server cannot verify the decrypted MIME, extension, image content, audio, orientation, visual quality, or GCM tags without vault keys. The local optimizer and decryptor must validate those; server checks only format/MIME consistency and envelope shape. The API accepts no plaintext filename.

The file insert and job completion share an Atlas transaction. A failed or uncertain commit leaves the UploadJob and exact object inventory for retry; it does not blindly delete an object that may have become a ready file. Completion is idempotent for the same committed metadata. Cancellation fences completion, checks for a ready file, destroys only the job's recorded Cloudinary object with `invalidate: true`, rechecks absence, then marks cleanup complete. A provider outage or unconfirmed deletion leaves a retryable job. `npm run uploads:reconcile -- --run` is a guarded, **manual** scan of expired unfinished jobs; it skips ready files, attempts cleanup, and reports counts without printing object IDs or credentials. No recurring scheduler is installed yet. Cloudinary CDN copies may remain temporarily accessible to someone holding an old signed URL after remote deletion; VaultX must never expose such a URL to browsers.

Automated tests use fake Cloudinary responses and a fake store to exercise missing objects, wrong type/identity, both byte caps, header tampering, repeated completion/cancellation, network and database failure. They do **not** establish live provider integration of these new routes. The previous 65 KiB synthetic provider probe predates this lifecycle, and the account's near-100 MB video limitation remains.

The proposed next transfer path is an owner-authenticated, same-origin **server-mediated ciphertext stream**. It must accept only locally encrypted v1 container bytes, enforce actual streamed byte count and manifest/header binding, use the server Cloudinary SDK with the fixed `raw/authenticated` options and no overwrite, and independently verify Cloudinary's stored `bytes`, type and ID. It must reconcile or delete failed/expired objects before marking a file ready. This path needs separate implementation and synthetic provider tests. The current Free plan's reported 10 MiB raw cap still blocks the PRD's near-100 MB single-object video case; a plan change or reviewed multi-object design is required.

They were placed only in the Git-ignored local `.env.local` at the owner's explicit request, but they should be rotated in Atlas and Cloudinary and updated locally. ## Proposed storage mode, pending account verification

Use Cloudinary `resource_type: raw` for **client-encrypted ciphertext** and provisionally choose `type: authenticated` for delivery. `raw` preserves bytes without image/video transformations; a ciphertext blob must not be treated as an image or playable video by Cloudinary. `authenticated` is preferable to `private` because Cloudinary documents that a `private` original needs a signed URL while transformed variants can be publicly delivered by default; authenticated originals and variants require signed delivery. The small raw-asset tests above passed on this account, but that does not prove all URL patterns, caches, extensions, or future settings are safe. [Cloudinary raw asset description](https://cloudinary.com/documentation/cloudinary_glossary), [media access rules](https://cloudinary.com/documentation/control_access_to_media), [upload API delivery types](https://cloudinary.com/documentation/image_upload_api_reference).

VaultX should keep Cloudinary URLs and signing credentials on the server. Future download/preview routes must first authenticate the owner and authorize the database record. Only then may they fetch ciphertext and return it to the client for local decryption. A Cloudinary signed delivery URL is itself a bearer capability; it is not a substitute for VaultX owner authorization. A normal signed delivery URL is not automatically short-lived. Cloudinary's `private_download_url` can create a time-limited signed URL, but its delivery and bandwidth behavior must be tested with `raw/authenticated` and the owner's plan. [Cloudinary media access methods](https://cloudinary.com/documentation/control_access_to_media).

### Video fallback decision

The PRD asks for playable, seekable, locally decrypted videos and a strict **final stored-object** threshold below 100 MB. This account's 10 MiB raw cap makes a single 95 MB ciphertext object infeasible on Free. Possible future choices are a provider plan with a verified larger raw cap or a reviewed encrypted segmentation design using several smaller raw objects and a manifest. Segmentation changes upload, range, retrieval, integrity, and deletion logic, so **it is not approved or implemented here**. Until a storage design is chosen and tested, P0 video storage remains **BLOCKED**. A small synthetic asset below the PRD's image byte limit passed the tested access and retrieval paths, but actual client-encrypted image upload, owner authorization, and app delivery have not been implemented or verified.

## How to get credentials privately

1. In the official [Cloudinary Console](https://console.cloudinary.com/), sign in or create your own account. Select the product environment for VaultX.
2. Open **Settings > API Keys**. This page shows the cloud name, API key, and API secret. The cloud name is also visible on the dashboard. [Cloudinary credential instructions](https://cloudinary.com/documentation/developer_onboarding_faq_find_credentials).
3. In VS Code's Explorer, create or open `D:\VaultX\.env.local` beside `package.json`. Add the following lines and enter your own values there:

   ```dotenv
   CLOUDINARY_CLOUD_NAME=your-cloud-name
   CLOUDINARY_API_KEY=your-api-key
   CLOUDINARY_API_SECRET=your-api-secret
   ```

4. Save the file and restart the development server after changing environment values. `.env.local` is ignored by Git. Do not put the secret in `.env.example`, a `NEXT_PUBLIC_` variable, browser code, screenshots, terminal output, or chat. VaultX does not need the combined `CLOUDINARY_URL` value.

## Required live test protocol after local configuration

The small-object subset of this protocol was executed on 2026-10-14 with deliberately generated, non-personal random bytes. Run `npx tsx scripts/probe-cloudinary.ts --live` only when you intend to create and delete new synthetic test objects. The script requires `--live`, and it keeps raw responses and URLs out of logs. Do not use an existing personal file. Remaining steps are still required before application uploads.

1. Confirm the three local environment variables are present and the SDK can make a read-only authenticated API request. A valid configuration shape alone does not prove Cloudinary accepted the credentials.
2. Use a small synthetic blob to test signed server upload as `raw/authenticated`. Confirm upload response `resource_type`, `type`, public ID, and `bytes` match the submitted bytes. Test `raw/private` separately only if needed to compare behavior; delete all test objects afterward.
3. From a fresh unauthenticated HTTP client, request every relevant unsigned original and alternate delivery URL. Verify no body contains the blob. Repeat after an authorized fetch has warmed caches. A 200 response to any anonymous route blocks that mode.
4. Test the intended restricted retrieval path, short expiry if supported, expiry after the deadline, and `Range` responses (`0-15`, a middle span, invalid range). Confirm exact bytes and `Content-Range`; retry after a new signature/owner session. Any missing range support blocks the current streaming design.
5. Test a signed direct upload with tightly constrained parameters and deliberately invalid/expired signatures. Confirm unsigned/default-public uploads cannot be used through VaultX. Do this only once the owner-authenticated signer exists.
6. Probe actual account raw upload caps using **synthetic** data only and stay within the plan's known quotas. Do not try a near-100 MB video object on a documented 10 MB raw cap. Measure storage, request, and bandwidth costs.
7. Destroy every test object with exact public ID, `resource_type: raw`, delivery type, and `invalidate: true`. Confirm a repeated delete is handled, asset lookup fails, and delivery links stop working after any documented CDN propagation interval. Record any backup or retention caveat.

**Release gate:** No real VaultX upload or media endpoint should be enabled until these provider checks pass, client-side encryption and owner authentication exist, actual ciphertext byte limits are enforced, and failed uploads/deletions have durable cleanup.
