# VaultX crypto and streaming contract (proposed v1)

**Status: LOCAL FILE-CONTAINER PROTOTYPE; NOT APPROVED FOR PERSONAL FILE UPLOAD.** This specifies an interoperable format and release gates for PRD §§7, 8, 10 and 15. Vault root-key wrapping, recovery setup, and local chunk encryption/decryption now exist. Upload, ciphertext proxy, playback and download do not. An independent cryptographic review and device/provider tests are required before storing personal files.

## 1. Threat boundary and decisions that block storage

VaultX authenticates a single owner on the server, while media optimization, encryption and decryption must run on the owner's device. The server and Cloudinary may see ciphertext bytes, object length, timing and some database classification fields. The server can authorize access and check Cloudinary's actual object size and delivery mode; it **cannot** prove decrypted MIME, playable codec, correct plaintext, or an AES-GCM tag without the file key. The client must verify those after decrypting. This design does not promise anonymity, traffic hiding, guaranteed memory erasure, or protection from malicious JavaScript served by a compromised VaultX origin, browser compromise, or an already unlocked device. Use HTTPS, strict CSP, dependency review and no third-party script on secret-bearing views.

**Key separation adopted for key setup:** The existing `/unlock` login sends the authentication password to the server for Argon2id verification. Deriving the vault wrapping key from that same password would let the server derive it too. The current setup therefore requires a **separate vault passphrase typed only into client-side key-unwrapping code**, plus an owner-held random recovery key. A future reviewed PAKE/OPAQUE-style login could change this. Do not call encrypted storage zero-knowledge until the full client, origin and recovery threat model is reviewed and tested. Never send the vault passphrase, recovery key or raw vault/file keys to a VaultX API or logs.

**Provider decision required:** `docs/CLOUDINARY_FEASIBILITY.md` records that this account reported a 10,485,760-byte raw-asset cap, and that only small synthetic `raw/authenticated` range reads were verified. A single nearly 100 MB video ciphertext object is therefore blocked on the current plan. A larger verified raw cap or a separately reviewed multi-object format is required. This v1 contract describes **one object per file or thumbnail**; splitting it silently across assets would break its offsets, byte limit accounting, inventory and deletion guarantees. Cloudinary signed URLs are bearer capabilities; the browser must use an owner-authorized VaultX ciphertext proxy, not receive permanent provider URLs.

## 2. Reviewed primitives and implementation rules

Use the platform [Web Cryptography API](https://www.w3.org/TR/WebCryptoAPI/) for AES-256-GCM, HKDF-SHA-256 and SHA-256. AES-GCM has a 256-bit key, 96-bit IV, 128-bit tag, explicit AAD, and WebCrypto's output is `ciphertext || tag`. Never release plaintext from a failed tag check. IV uniqueness under a key is mandatory under [NIST SP 800-38D](https://csrc.nist.gov/pubs/sp/800/38/d/final). Draw each vault root key, content key, salt, nonce prefix, UUID and recovery key with `crypto.getRandomValues`; do not use `Math.random` or derive file keys from a password directly.

Use a separately reviewed, maintained **browser** Argon2id implementation for vault-passphrase wrapping. The [RFC 9106](https://www.rfc-editor.org/info/rfc9106/) memory-constrained reference setting is 64 MiB, three passes, four lanes, 16-byte salt and 32-byte output. The current browser prototype uses [`hash-wasm` Argon2id v1.3](https://github.com/Daninet/hash-wasm/blob/master/README.md) with 64 MiB, three passes, **one lane**, a 16-byte salt and 32-byte output in a disposable Web Worker. This is an implementation choice awaiting independent review and low-memory phone benchmarks, not a measured mobile guarantee. The exact parameters are recorded in each envelope; unsupported/weaker parameters fail closed. Server-side login Argon2id parameters do not establish browser feasibility. HKDF-SHA-256 follows [RFC 5869](https://www.rfc-editor.org/info/rfc5869/); use domain-separated `info` strings and fresh salts. No home-grown cipher, unauthenticated CBC/CTR, shortened GCM tags or deterministic file keys.

Each immutable file and each thumbnail gets its **own random 32-byte content key**. For one object, choose a random 8-byte nonce prefix once and use `prefix || uint32be(index)` as the 12-byte GCM IV. Content chunk indexes are `0..N-1`; `0xffffffff` is reserved for encrypted metadata. At most `0xfffffffe` content chunks are allowed. A retry must re-upload the **identical cached ciphertext** or create a wholly new key, prefix, file UUID and object identity. Never encrypt different bytes with the same content key and IV, even after a crash. Do not accept a caller-supplied key, nonce or chunk index without enforcing these invariants.

## 3. Immutable v1 object wire format

All integers are unsigned big-endian. Byte offsets are zero-based. The header is exactly 80 bytes and contains no filename, MIME or provider ID. `file UUID` is a client-generated random 16-byte value mapped to an authorized MongoDB record; it is not the MongoDB `_id`. A thumbnail has its own 16-byte random `variant ID`; the main file uses 16 zero bytes. Unknown version, kind, flags/reserved values or noncanonical lengths fail closed.

| Header offset | Bytes | Field | v1 rule |
| ---: | ---: | --- | --- |
| 0 | 8 | Magic | ASCII `VAULTX01` |
| 8 | 2 | Format version | `1` |
| 10 | 2 | Kind | `1` file; `2` thumbnail |
| 12 | 4 | Header length | `80` |
| 16 | 16 | File UUID | Cryptographically random; record-bound |
| 32 | 16 | Variant ID | All zero for main file; random and nonzero for thumbnail |
| 48 | 8 | Plaintext length `L` | Stored optimized bytes, before encryption |
| 56 | 4 | Plaintext chunk size `C` | `1,048,576` bytes |
| 60 | 4 | Chunk count `N` | `max(1, ceil(L/C))`, at most `0xfffffffe` |
| 64 | 8 | Nonce prefix | Random per content key/object |
| 72 | 4 | Encrypted metadata length `M` | Includes GCM tag; `16..65,552` |
| 76 | 4 | Reserved | Zero |

The body is `80-byte header || M-byte encrypted metadata || chunk[0] || ... || chunk[N-1]`. Metadata is UTF-8 JSON with a strict versioned schema and bounded lengths; its bytes are encrypted with the content key, reserved metadata IV, 128-bit tag and AAD `UTF8("VaultX/meta/v1\0") || header[0..79]`. Include the stored filename/extension, actual locally inspected MIME/signature, SHA-256 of the complete stored plaintext, optimized codec/dimensions/duration when applicable, optional thumbnail relationship and, for video, the fMP4 init and fragment time/byte index. The metadata is immutable with the object. Folder moves, display-name edits and other mutable fields use a **separate versioned AEAD metadata envelope** with a fresh nonce and record/field AAD; they do not rewrite this object's header or reuse its IV. Plaintext names must never be stored in ordinary MongoDB fields or logs.

Folder names now use `VaultX/folder-name/v1\0 || vaultUUID || folderID` as the HKDF info, a fresh 32-byte salt, and the unlocked vault root key to derive AES-256-GCM keys. Each name has a fresh 12-byte nonce and AAD `VaultX/folder-name-aad/v1\0 || vaultUUID || folderID`. Rename creates a new envelope; moving changes only the parent ID. The server checks envelope shape and vault ID but cannot verify the plaintext name or tag. Names are decrypted only in the unlocked browser.

For content chunk `i`, define `P_i = min(C, max(0, L - i*C))`. Even an empty file has one zero-byte plaintext chunk and one 16-byte tag. Encrypt each chunk under its content key with IV `prefix || uint32be(i)`, 128-bit tag and exact AAD:

```text
UTF8("VaultX/chunk/v1\0") || header[0..79]
  || uint32be(i) || uint64be(i*C) || uint32be(P_i)
```

The binary container offsets are:

```text
metadata bytes: [80, 80+M-1]
chunk i start:  S_i = 80 + M + i*(C+16)
chunk i end:    E_i = S_i + P_i + 16 - 1   (inclusive)
total object:   T = 80 + M + L + 16*N
```

Reject `L`, `M`, `N`, offsets or object sizes outside their bounds; use integer-safe arithmetic (`bigint` in JavaScript), and reject any trailing/missing bytes. Validate the full header against the authorized record's immutable manifest and provider-reported `T` before chunk requests. The header alone is untrusted until an AEAD tag is verified; metadata and every decrypted chunk authenticate the **entire** header through AAD. Never stream unauthenticated plaintext to a decoder or download sink. Chunk tags prove only the chunks fetched. Full-file integrity requires verifying all chunks; a complete, older valid object or database envelope can still be replayed unless a trusted external freshness anchor is added. Do not advertise rollback protection.

**Golden layout vectors** (also in `tests/crypto-format-v1.test.ts`): for `L=2,097,159`, `M=32`, `N=3`, ciphertext chunk ranges are `112-1,048,703`, `1,048,704-2,097,295`, `2,097,296-2,097,318`, and `T=2,097,319`. For `L=0`, `M=16`, `N=1`, the empty chunk's tag is at `96-111` and `T=112`. With `M=32` and one chunk, plaintext length `999,871` yields a `999,999`-byte object, while one more plaintext byte reaches the disallowed `1,000,000` bytes. These are arithmetic-only vectors; real encrypted JSON metadata will be longer. A standard AES-256-GCM zero-key/zero-IV/empty-plaintext vector has tag `530f8afbc74536b9a963b4f1c4cb738b`; this checks the primitive, **not** full container interoperability.

## 4. Key envelopes, password changes and device unlock

Generate a random 32-byte vault root key `VRK` and random 16-byte vault UUID at initial key setup. Keep `VRK` in volatile client memory only while unlocked. The authenticated server stores encrypted envelopes and serves them only to the owner; it never needs unwrapped keys. Store a complete envelope schema version, identifier, KDF parameters, salt, nonce, ciphertext and tag. Reject unknown versions and missing fields; bind identifiers with AAD. No envelope may contain a raw key.

- **Per-object key wrap:** derive a 32-byte AES-GCM wrapping key as `HKDF-SHA-256(VRK, fresh 32-byte salt, info, 32)`, where `info = UTF8("VaultX/file-key/v1\0") || vaultUUID || fileUUID || variantID || uint32be(wrapRevision)`. Wrap the 32-byte content key with a fresh 12-byte IV and AAD `UTF8("VaultX/file-key-aad/v1\0") || vaultUUID || SHA256(header[0..79]) || uint32be(wrapRevision)`. The `salt`, IV and revision are stored beside the 48-byte ciphertext-plus-tag. A rewrap uses a new salt, IV and increasing revision; a copied envelope cannot be substituted for a different header/variant. Owner authorization still binds the MongoDB record to the object identity.
- **Vault-passphrase wrap:** derive a 32-byte AES-GCM key locally with Argon2id from the **separate vault passphrase** and a fresh 16-byte salt. Encrypt `VRK` with a fresh 12-byte IV and AAD `UTF8("VaultX/passphrase-wrap/v1\0") || vaultUUID || uint32be(1)`. Store only salt, reviewed KDF parameters, IV and the 48-byte encrypted root key. Apply a local envelope integrity check after decryption; failed unlocks must not expose detail or release a key. Offline password guessing against a stolen envelope remains possible, so require a strong vault passphrase and tuned KDF.
- **Recovery wrap:** generate an independent random 32-byte recovery secret locally. Show it once for offline owner backup. Derive a 32-byte AES-GCM wrap key with HKDF-SHA-256, a fresh 32-byte salt, and `info = UTF8("VaultX/recovery-wrap/v1\0") || vaultUUID || uint32be(1)`. Encrypt `VRK` with a fresh 12-byte IV and the same domain, UUID and format version as AAD. Store only the encrypted recovery envelope. Losing both passphrase and recovery secret can permanently lose the files; neither a PIN nor a successful WebAuthn assertion alone regenerates `VRK`.

The envelope's top-level `revision` is a **database compare-and-swap counter**, initially 1 and incremented when the password wrap changes. It is not the cryptographic wrap format version. Both wraps keep the v1 context shown above, so replacing the password wrap does not invalidate the independent recovery wrap. Each new password wrap draws a fresh random salt and nonce. A future change to either wrap format requires a new explicit format version and migration; the counter must never be substituted into the existing v1 AAD.

Changing the **login password** updates server authentication and does not re-encrypt files. Changing the **vault passphrase** requires the current `VRK` (obtained with old passphrase or recovery), creates and verifies a new passphrase envelope, atomically replaces the active envelope, and invalidates previous sessions as policy requires. Changing the passphrase does not revoke a previously copied old envelope plus old passphrase; true root-key rotation requires a reviewed rewrap of every content key, and compromised content keys require re-encrypting those objects. Recovery-secret rotation likewise needs a new recovery envelope and safe acknowledgement; do not delete the only usable envelope during a partial failure.

On a second device, the owner first logs in to get an authorized session, then fetches the encrypted root-key envelope and uses the vault passphrase or recovery secret **locally** to unwrap `VRK`; only then can it unwrap object keys and metadata. There is no server-held rescue key. A convenience PIN or biometric device credential may only unlock through an explicitly reviewed device-bound key mechanism, not by silently weakening the passphrase design. On lock/logout/background timeout, stop requests, release media buffers and best-effort clear app-held key buffers; JavaScript/browser/OS copies cannot be guaranteed erased.

**Prompt 34 convenience authentication:** a six-digit PIN or user-verified platform passkey can create a fresh owner *session* after prior password-authenticated enrollment. The PIN uses a browser-profile HttpOnly random token plus a salted Argon2id verifier and a server-side five-attempt lockout. The token is copyable with the browser profile, so this is not a hardware security guarantee. WebAuthn stores only credential public key/counter and checks a one-use challenge, exact configured origin/RP ID, and user verification. Neither method unwraps `VRK`; the owner still enters the vault passphrase or recovery key after lock. No root key or password-derived wrapping key is put in localStorage or IndexedDB. A future PRF/device-bound unwrap is a separate reviewed migration and must prove device/browser interoperability and key recovery before being offered.

Thumbnails are separately optimized and encrypted with their own random content key, nonce prefix, header, wrapped key and `raw/authenticated` object ID. Their encrypted metadata can reference the parent UUID/variant ID. MongoDB upload and deletion jobs must inventory **every** main and thumbnail object for cleanup. Cloudinary cannot transform encrypted originals into private thumbnails.

## 5. Current local implementation and integration boundary

`src/lib/crypto/file-container.ts` implements this v1 header, metadata AAD, per-chunk AAD, fresh content keys/nonces, HKDF key wrapping, strict parsing, bounded `Blob.slice` reads, exact object-size accounting and chunk-range decryption. `prepareEncryptedFile` and `prepareEncryptedThumbnail` return a **one-use async ciphertext stream** and a manifest; the thumbnail API expects a Blob already generated locally. It does not create or inspect thumbnails or validate MIME/signatures/codecs. `openEncryptedContainer` takes a bounded ciphertext-range source and checks exact header, metadata and chunk lengths. Its `decryptChunk` authenticates only that chunk; its `chunks` iterator also checks the whole-plaintext SHA-256 at completion. Callers must close readers and dispose unconsumed writers. Lock invalidates operations and wipes app-held mutable key buffers where practical. JavaScript strings, CryptoKey internals and buffers copied by the browser cannot be guaranteed erased.

The manifest contains the immutable header, per-object wrapped content key and predicted total bytes; it contains no plaintext filename. The encrypted metadata stores a **caller-supplied** name, extension and MIME hint plus a locally computed plaintext SHA-256. A future local media pipeline must inspect and validate content before passing those fields, and the authenticated server must bind the manifest, owner, file and thumbnail identities to database records. Size rejection happens before ciphertext is emitted using `T = 80 + M + L + 16*N`, including all tags. A completed stream checks emitted bytes against `T`; this is still a **client prediction**. Before any file is marked ready, the server must independently verify Cloudinary's actual stored ciphertext bytes, type, delivery restrictions and exact ID. This module does not upload, persist, or silently assemble decrypted files.

Synthetic Node/WebCrypto tests cover empty, boundary, multi-chunk, thumbnail separation, range offsets, altered bytes, wrong key, lock, truncation and trailing bytes. Browser interoperability, adversarial review, interrupted upload retry, producer/consumer cancellation and actual phone memory use remain to be tested before deployment.

## 6. Authenticated ciphertext ranges and playback

The browser requests an owner-scoped VaultX range endpoint for an authorized file record. The server checks the current owner session and lock state on **every** request, confirms the record is `ready` and not deleting, chooses Cloudinary's exact stored ID/type from MongoDB (never from the URL/body), and streams only ciphertext with `Cache-Control: private, no-store`, `Referrer-Policy: no-referrer` and no public signed URL. Invalid/anonymous/locked/deleting requests reveal no private resource existence. Apply bounded single-range parsing, rate/resource limits, abort propagation, no compression or transformation of ciphertext, and disable service-worker/private browser caching. An already issued Cloudinary signed URL may remain retrievable after deletion; never expose it to the client. Range response behavior follows [RFC 9110](https://www.rfc-editor.org/rfc/rfc9110.html).

The client first fetches the 80-byte header and bounded encrypted metadata, checks exact `206`, `Content-Range`, total `T`, response byte length and immutable record match, unwraps the content key and authenticates metadata. For each desired plaintext span, round outward to complete GCM chunks using `[S_i,E_i]`, request only those ciphertext ranges, validate exact `206`/range/total and decrypt the **whole** chunk before exposing any bytes. Do not accept a provider/proxy `200` full-object response to a range request; abort it without buffering. Reject mixed-object/ETag changes, mismatched total, truncated responses and unsupported multipart responses. Bind all chunk requests to the same immutable object version; `If-Range`/ETag may help, but authenticated header/record comparison remains required. Server confirmation of Cloudinary `bytes == T`, raw/authenticated delivery type, exact public ID and decimal media cap (`image <1,000,000`, `video <100,000,000`) is separate from client AEAD/plaintext verification. A server cannot truthfully verify decrypted MIME or video decodability; do those checks locally before encryption and again on decryption where practical.

For MP4, local optimization must produce **fragmented MP4** with H.264/AAC, an `ftyp+moov` initialization segment and independent keyframe-aligned `moof+mdat` media fragments. Record each fragment's plaintext byte start/end, decode/presentation time, duration and keyframe seek point in the encrypted metadata. Ordinary fast-start MP4 with one `moov` and a huge `mdat` is insufficient for the proposed MediaSource append/seek path. Enforce a bounded init segment and fragments (candidate at most 4 MiB each, to be tested); fail the local encode when the media cannot meet codec, fragment, quality, metadata-size or ciphertext-size constraints. Validate fMP4 boxes and the fragment index locally; [W3C's ISO BMFF MSE byte-stream format](https://www.w3.org/TR/mse-byte-stream-format-isobmff/) has additional `tfdt`, relative-addressing and sample rules.

On browsers that pass `MediaSource.isTypeSupported()` with the exact generated H.264/AAC codec string and a real playback probe, create a `MediaSource`/`SourceBuffer`, fetch/decrypt only the init bytes and a few nearby fragments, append in timestamp order, and evict old buffered ranges. Seeking maps time to the nearest preceding independent fragment, requests only its enclosing encrypted chunks, decrypts/validates them, then resumes appending from that fragment. Bound concurrent ciphertext, decrypted fragments and decoder buffer; cancel outstanding fetches and revoke object URLs on lock. Use a worker where feasible so decryption/assembly does not freeze the UI. This is a design to test, not a compatibility claim. The [MSE API](https://www.w3.org/TR/media-source-1/) and WebKit's [iPhone Managed Media Source notes](https://webkit.org/blog/14735/webkit-features-in-safari-17-1/) make phone behavior especially important to verify, including installed PWA mode. Do not silently fall back to a 100 MB decrypted Blob, a public media URL or plaintext server transcode. If MSE or the necessary codec path fails, show an honest playback limitation and test a separately reviewed bounded-memory native/HLS alternative before claiming PRD playback acceptance.

Authenticated downloads likewise decrypt chunk-by-chunk and write stored optimized bytes to a reviewed bounded-memory browser save path. If a device cannot save large files without materializing the whole plaintext in RAM, block that large download on that device and report the limit; do not silently send plaintext to a server or remote processor. A partial seek proves only the fetched chunks; a completed download must authenticate every chunk and verify any stored full-file digest/length on the client. Before showing previews or choosing extensions, inspect decrypted signatures/MIME locally, allowlist safe renderers and never execute active content as same-origin HTML.

## 7. Schema, migration and operational consequences

The `fileSchema.encryptionManifest` now accepts the full v1 manifest for a future verified ready file, alongside an older limited schema for legacy/test records. UploadJobs reserve a v1 manifest and opaque Cloudinary object ID, and the completion path persists the wrapped key, encrypted display name and provider-confirmed object identity/bytes. The server compares the stored ciphertext header but cannot authenticate its GCM tags or decrypted media without the owner's key. There is still no ciphertext transfer or server-recorded upload receipt in ordinary use; thumbnail variants, exact file/variant relations, periodic cleanup scheduling and live completion tests remain. **Do not treat this as a working encrypted upload path.** Continue to keep raw filenames and key material out of MongoDB and logs. Existing login/session code grants access; it is not a cryptographic unlock or media path.

Format version `1` and envelope versions are explicit. Readers dispatch only on known versions and never reinterpret unknown headers. A future codec/container or multi-object change gets a new format version with migration code and cross-version fixtures; old decryptors remain available until every object is migrated. Migrate by locally decrypting/authenticating the old object, producing a new key/nonce/object/manifest, verifying its Cloudinary byte size and retrievability, atomically switching the active MongoDB record, then durably deleting the old object. Interrupted migrations remain retryable and keep the old readable version. Never mutate ciphertext in place, reuse a nonce during migration, or infer a version from file extension.
