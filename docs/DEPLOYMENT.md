## Choose the hosting path

| Path | Current result | What is needed |
| --- | --- | --- |
| **Vercel Functions (preferred)** | **BLOCKED by this repository's `prebuild` gate.** The browser sends an entire ciphertext object through `PUT /api/uploads/[id]/ciphertext`, up to 10,000,000 bytes. Vercel limits a Function **request** body to 4.5 MB. Ordinary buffered responses also have a 4.5 MB limit; Vercel documents streaming-response behavior separately, but this app's complete large-object gateway and browser range path have not been verified there. Increasing Function duration or buying a different Cloudinary plan does not remove the request limit. [Vercel limits](https://vercel.com/docs/functions/limitations), [large-body guidance](https://vercel.com/kb/guide/how-to-bypass-vercel-body-size-limit-serverless-functions). | Design, implement and test browser-direct **ciphertext-only** signed upload with immutable opaque IDs, short-lived least-privilege intent, provider verification and durable cleanup; also verify a bounded authenticated download/range strategy on Vercel. Re-run all security/acceptance tests, then remove the build gate. Do not send plaintext directly to Cloudinary. |
| **Compatible long-running Node.js host** | Buildable and suitable for a controlled test deployment **if** its proxy permits at least 10 MB binary request bodies and bounded byte-range responses, has stable outbound access to Atlas, runs Node 24, and has an independent scheduled worker. This does not resolve the full video acceptance gate. | Configure HTTPS reverse proxy, restricted network/database access, process supervision, separate reconciliation schedule and monitoring. Next.js recommends a reverse proxy for self-hosting. [Next.js self-hosting](https://nextjs.org/docs/app/guides/self-hosting). |

The configured Cloudinary account previously reported a **10,485,760-byte raw-asset cap**. The application itself caps current transfers below 10,000,000 bytes. The PRD's near-100 MB encrypted video cannot fit one object on that account; a verified higher raw cap **and** a reviewed fragmented-MP4 seek path (or a separately reviewed encrypted multi-object design) are still needed. See [feasibility](CLOUDINARY_FEASIBILITY.md) and [acceptance matrix](ACCEPTANCE_MATRIX.md). A Cloudinary plan upgrade alone does not make current Vercel upload/download work.

## Before a GitHub push

1. In VS Code, choose **Terminal → New Terminal**. Run `git status --short` and `git check-ignore .env.local`. The second command must print `.env.local`. Review every file that would be committed; `.env.local`, `.env`, backups, downloaded exports and screenshots with private content must remain out of Git. The repository currently has many uncommitted files, so review the diff before publishing.
2. Run `npm ci`, `npm run verify:production`, and `npm run test:e2e` on your computer. The latter uses installed Chrome and a production build. Run `npm run security:bundle-check` again whenever production environment variables change. `verify:production` runs lint, typecheck, the unit/contract suite, production build and the public-bundle secret scan.
3. Rotate the MongoDB database password and Cloudinary API secret that were previously exposed in chat, then update only your ignored local environment and future host's **Secret** variables. Do not put replacement values in chat, a commit, an issue, a screenshot or a build log. Rotating the existing login password is also prudent if it was shared.
4. Run `npm run security:git-check` and create a **private** repository in GitHub (**New repository → Private → Create repository**). Use GitHub Desktop (**File → Add local repository → choose `D:\VaultX` → Publish repository**) or Git commands after reviewing the staged files. There is no remote configured yet. Review the entire large uncommitted worktree and the intended commit before publishing; the scan checks configured exact values, not every possible secret or private file. Do not publish until this review passes. Grant access only to trusted maintainers.

## Vercel import preparation (deployment remains blocked)

These steps prepare project settings. **Do not remove the build guard or use the result for personal files** while the first table is blocked.

1. Sign in at [Vercel](https://vercel.com/dashboard). Choose **Add New → Project** (or **New Project**), connect GitHub, select your private VaultX repository and click **Import**. Set Framework Preset to **Next.js** and Root Directory to the repository root. The normal Build Command is `npm run verify:production`, but the current `prebuild` intentionally fails on Vercel. [Vercel Git import](https://vercel.com/docs/git).
2. In **Project → Settings → Build and Deployment → Node.js Version**, select **24.x**, matching `package.json` and the tested local Node major. Vercel lists 24.x as a supported Function/build runtime. [Node versions](https://vercel.com/docs/functions/runtimes/node-js/node-js-versions).
3. In **Project → Settings → Environment Variables**, add each server credential separately, select **Production** only and choose **Secret** visibility. As of August 2026 Vercel calls the write-only choice **Secret** rather than the older **Sensitive** toggle. Environment changes apply to new deployments, so redeploy after changing one. [Vercel variables](https://vercel.com/docs/environment-variables), [Config/Secret change](https://vercel.com/changelog/environment-variables-now-use-config-and-secret-types).
4. Keep Preview deployments disconnected from your live Atlas database and Cloudinary account. Use a separate disposable test environment if you need functional previews; never copy production credentials into Preview. Do not put secret variables under `NEXT_PUBLIC_`.
5. Under **Project → Settings → Domains**, add the single canonical domain you intend to keep. Follow the displayed DNS instructions and wait for Vercel's certificate to be valid before setting `WEBAUTHN_ORIGIN`. If you later change domains, registered passkeys may need reenrollment. [Domain setup](https://vercel.com/docs/domains/set-up-custom-domain).

### Environment variable names

| Name | Visibility and meaning |
| --- | --- |
| `MONGODB_URI` | **Secret**, Atlas application user's rotated TLS connection string. Never paste it into Git or chat. |
| `MONGODB_DB_NAME` | Config, production database name. Use a separate name/database for disposable tests. |
| `CLOUDINARY_CLOUD_NAME` | Config, dedicated Cloudinary environment name. |
| `CLOUDINARY_API_KEY` | **Secret**, server SDK credential. |
| `CLOUDINARY_API_SECRET` | **Secret**, rotated server SDK credential. |
| `WEBAUTHN_ORIGIN` | Config, exact canonical HTTPS origin such as `https://vault.example.com` with **no trailing slash**. Required to use passkeys in production. |
| `WEBAUTHN_RP_ID` | Config, canonical hostname such as `vault.example.com`. |
| `NEXT_PUBLIC_APP_URL` | Public config name retained from the PRD template; current app code does not read it. If set, use only the canonical HTTPS origin. Never place secrets here. |
| `AUTH_SECRET` | **Secret**, at least 32 random bytes. Auth.js encrypts its session cookie with it. Keep the existing value when suitable; changing it invalidates Auth.js sign-ins. MongoDB opaque sessions remain required for revocation and lock. |
| `AUTH_OWNER_EMAIL` | **Secret/config**, the single authorized owner email. Set it in the host's server-only environment and keep it out of browser bundles. |
| `NEXTAUTH_URL` | Config, exact canonical HTTPS origin used by Auth.js callbacks. It must match the deployed domain. |

All API routes needing MongoDB/Cloudinary already select the **Node.js runtime**. The browser transcodes locally; no serverless function is used as a video encoder. The production session cookie is `HttpOnly`, `SameSite=Strict`, `Secure` and `__Host-` prefixed. The app sends nonce-based CSP on document responses, no-store on private routes, HSTS on production responses and a restrictive referrer policy. Verify these again on the actual HTTPS domain; local HTTP checks do not prove proxy behavior. The service worker only caches public shell resources, and reopening the app must respect lock policy.

## Atlas and Cloudinary access

1. In [MongoDB Atlas](https://cloud.mongodb.com/), select the VaultX project. Open **Security → Database & Network Access → Database Users** and use a dedicated application user with only the role needed for the VaultX database (`readWrite` plus the index setup permissions during provisioning). Do not use a project/admin credential as `MONGODB_URI`. Rotate the exposed password.
2. Open **Security → Database & Network Access → IP Access List**. Allow only the chosen host's stable outbound IPs. Atlas connects only from listed IPs; `0.0.0.0/0` allows connections from anywhere and is not the deployment plan for this private vault. [Atlas IP list](https://www.mongodb.com/docs/atlas/security/ip-access-list/).
3. Vercel outbound IPs are dynamic by default. Vercel documents Static IPs for Pro/Enterprise and Secure Compute for Enterprise; enable one of these and allowlist its displayed egress IPs before expecting a Vercel-to-Atlas connection. A compatible Node host with fixed egress is another option. [Vercel outbound IPs](https://vercel.com/kb/guide/how-to-allowlist-deployment-ip-address).
4. In the [Cloudinary Console](https://console.cloudinary.com/), rotate the API secret and use a dedicated product environment if available. VaultX stores **client-encrypted ciphertext** as `resource_type: raw`, `type: authenticated`, with opaque IDs. Do not change it to `upload` or publish provider URLs. Re-run the disposable unsigned-original, alternate-public-URL, exact-range and deletion checks after any account security or plan change. A previously signed URL served bytes briefly after deletion in an earlier live probe; active-store deletion is not immediate CDN or backup erasure.

## Owner and worker on a compatible Node host

Provision a host that runs the app as a restricted service account behind an HTTPS reverse proxy. Configure the proxy's request body allowance for at least the current 10,000,000-byte ciphertext transfer, preserve `Range` and `Content-Range`, and set bounded upload/read timeouts. Serve one canonical HTTPS hostname; forward the original host/protocol correctly so origin/CSRF checks see the real origin. Block public access to the host's internal Node port. Put environment values in the host's secret manager or a protected service environment outside the Git checkout. Install Node 24, run `npm ci`, then `npm run verify:production` and `npm run start` under a restartable service. Confirm the host's backup and disk retention policies do not capture plaintext: VaultX only persists ciphertext and encrypted metadata, but local browser downloads are outside server control.

On a **new empty production database**, run `npm run db:indexes`, then `npm run owner:status`. Only if it says no owner exists, run `npm run owner:bootstrap` in an interactive private terminal and enter a new strong owner password into the masked prompt. Confirm `npm run owner:status` then says exactly one owner. Do not run bootstrap against an existing personal owner database to simulate first installation; do not paste the password into a shell command. Save the separate vault recovery key offline during the first authorized key setup.

Run `npm run recovery:run -- --run` as a **separate scheduled process** with the same server-only Atlas and Cloudinary environment, from the project working directory. Schedule a bounded pass every 15 minutes on a supported external job runner or stable host scheduler; alert on nonzero exit and inspect the Deletions page for failed/manual-retry jobs. The script uses durable MongoDB leases, returns counts without IDs or filenames, and exits nonzero when jobs remain deferred. A schedule is **not installed by this repository**. Vercel Hobby cron is at most daily and imprecise; Vercel cron invokes a Function with its normal duration limits, so it cannot replace an unlimited worker. [Vercel cron limits](https://vercel.com/docs/cron-jobs/usage-and-pricing). Owner-admin checkpoints can run the bounded protected reconciliation route when scheduling is temporarily unavailable.

For a Linux host using systemd, review the sample [service](../deploy/systemd/vaultx-reconcile.service) and [timer](../deploy/systemd/vaultx-reconcile.timer). They assume the checkout is `/srv/vaultx`, a restricted `vaultx` system user exists, and `npm` is `/usr/bin/npm`; confirm each path on your host before copying them. In the host terminal, create `/etc/vaultx/production.env` with the database and Cloudinary variables using a private editor, owned by root and mode `0600`; never store it in the checkout. Copy the two unit files to `/etc/systemd/system/`, then run `sudo systemctl daemon-reload`, `sudo systemctl enable --now vaultx-reconcile.timer`, and `systemctl list-timers vaultx-reconcile.timer`. Run one pass with `sudo systemctl start vaultx-reconcile.service`; inspect only redacted counts with `journalctl -u vaultx-reconcile.service -n 30`. A failing service needs an alert from your host monitoring. These templates do **not** run on Windows or install themselves on Vercel.

## Verify the actual production URL before personal use

Use disposable synthetic files only. Keep a redacted record of date, host, status and response code. The commands below ran locally or against isolated service test data in the [acceptance matrix](ACCEPTANCE_MATRIX.md); **none proves an uncreated production URL**.

1. Visit `https://YOUR-DOMAIN/unlock`. Confirm a valid certificate and that HTTP redirects to HTTPS. Open browser DevTools → Network → `/unlock` and check CSP, HSTS, `Referrer-Policy: no-referrer` and `Cache-Control: no-store`. Sign in, inspect the session cookie flags without copying its value, lock and confirm `/api/files` and a prior `/api/files/ID/access` return 401.
2. Confirm `/signup`, `/register` and `/share` return 404. From a clean/incognito browser, request the tested unsigned Cloudinary `raw/authenticated` URL and alternate `raw/upload` URL for a **disposable test object**; neither may return ciphertext. Do not copy a signed URL into tickets or chat.
3. Upload a disposable locally generated image and small video, ensure the job reaches ready only after Cloudinary reports the exact stored ciphertext bytes and restricted type, and try preview and download. A 10 MB source-image journey, large video and bounded encrypted seek remain **BLOCKED** as recorded in PRD §16. Use the guarded `npm run uploads:integration-check` and `npm run media:access-check` for isolated small-service verification; they do not exercise the deployed UI.
4. Test authenticated ciphertext `Range` reads for exact `206` and `Content-Range`, invalid range `416`, cancellation and lock revocation. A small signed provider range is **not** proof of full browser encrypted video seek. The current fragmented-MP4 acceptance is blocked.
5. Delete disposable file and nested folder test data. Check Cloudinary Admin lookup and Atlas active records, wait for job completion and verify siblings remain. Run `npm run deletions:live-check` for an isolated single-object service test; recursive live-provider deletion remains unverified.
6. Install/open on physical Android Chrome and iOS Safari Home Screen. Confirm app refresh/resume locks, no private service-worker cache and passkey origin behavior on the canonical HTTPS domain.

## Monitoring and known limits

`src/instrumentation.ts` emits only `vaultx_unhandled_request_error area=<fixed category>` for unhandled server errors. It does not forward the error, request, URL, headers or user content. Watch this signal, HTTP 5xx and nonzero worker exits; investigate using aggregate codes and disposable reproduction. Do not install an error SDK with automatic breadcrumbs, request-body capture, session replay or browser recording without a separate privacy review. Vercel's own runtime logs can include actual request paths and request metadata even when app logging is redacted; restrict access and retention. [Vercel runtime logs](https://vercel.com/docs/logs/runtime).

`npm audit --omit=dev` reported **0 runtime vulnerabilities** on 2026-10-23. Full `npm audit` reported **5 high** advisories in the development lint dependency chain (`eslint-config-next` → glob/micromatch/braces); these are unresolved and need review before a public build pipeline. No forced major downgrade/upgrade was applied. Re-run the audit before release.
