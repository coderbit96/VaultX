# New-video segmented encryption plan

Owner decision on 2026-10-23: new videos may use multiple small encrypted objects in the **existing Cloudinary account**. Existing objects, credentials, records, and videos remain untouched. This document is an implementation contract, **not a working large-video playback claim**. The current v1 path can load a small authenticated MP4 into a temporary browser Blob; it does not meet the bounded streaming criterion. Larger or unsupported videos remain download-only until a v2 path passes its tests.

## Verified constraints

- The Cloudinary Usage API reported a Free-plan `raw_max_size_bytes` of **10,485,760** on 2026-10-23. A near-100 MB single raw object cannot fit. Small `raw/authenticated` objects denied unsigned original delivery (HTTP 401) and allowed valid signed byte ranges (HTTP 206). Cloudinary returned HTTP 200 for an unsatisfiable upstream range in the latest probe, so the gateway must reject any non-206 response to a range request.
- Vercel's current request-body limit described in [deployment guidance](DEPLOYMENT.md) is below the current 10 MB single-object upload path. Target **at most 3,800,000 encrypted bytes per v2 object**, including every header, tag and frame. This headroom is a design limit, not proof of successful Vercel deployment. Other file categories still need a compatible transfer path.
- Enforce **strictly less than 100,000,000 total stored ciphertext bytes per video across all objects**, not just each object. The optimizer must reject output below the quality floor or above this aggregate limit. Keep the user's original outside VaultX; it is never uploaded or silently deleted.

## Versioned data path

1. Browser-local FFmpeg produces H.264/AAC fragmented MP4: one `ftyp+moov` initialization segment, then keyframe-aligned independent `moof+mdat` fragments. Validate actual boxes, `mvex`, `tfdt`, relative addressing, codec string, rotation, audio, duration and every fragment boundary against the [W3C ISO BMFF MSE format](https://www.w3.org/TR/mse-byte-stream-format-isobmff/). FFmpeg supports fragmentation flags, but a successful FFmpeg exit alone is insufficient. [FFmpeg format documentation](https://ffmpeg.org/ffmpeg-formats.html).
2. Pack complete initialization/media fragments into ordered groups whose **encrypted** objects each stay at or below 3,800,000 bytes. Do not split a media fragment across objects. Reject a fragment that cannot fit. Generate a fresh random data key and unique nonce domain for every object. Bind vault ID, server-reserved file ID, object ordinal, MP4 plaintext byte span, presentation/decode time span, codec and format version into authenticated metadata/AAD. Protect the complete ordered index with a vault-key-authenticated manifest; reject missing, reordered, overlapping, duplicated or swapped objects.
3. Reserve all opaque `vaultx/ciphertext/<random>.dat` IDs in one durable UploadJob before transfer. The server accepts only the reserved ordinal and fixed `raw/authenticated` mode. Upload **only ciphertext**. After each transfer, verify exact provider asset ID, public ID, version, delivery/resource type and stored bytes. A File becomes `ready` only after **every** object and the manifest are verified. Cancellation, expiry, provider outage, uncertain DB commit and retry retain the complete cleanup inventory.
4. Add owner- and state-checked per-object ciphertext range access. Client requests use file ID and ordinal; the server selects the provider identity from Atlas and rechecks session/lock on each request. Use no-store responses and reject upstream 200, malformed 206, length mismatch or object-version mismatch. Never expose signed Cloudinary URLs or accept client public IDs.
5. The unlocked browser authenticates an entire small object before appending its fMP4 bytes to a `MediaSource`/`SourceBuffer`. Check `MediaSource.isTypeSupported()` for the exact stored codec string. Seek to the nearest independent fragment, fetch only nearby objects, append in order, evict old buffered ranges, and cancel/clear on seek, lock, logout or unmount. Keep a bounded count of encrypted, decrypted and decoder buffers. Unsupported browsers receive an honest download-only state, never a whole-file Blob playback fallback labeled streaming.
6. Downloads decrypt and write ordered objects through a bounded browser file writer, authenticate the full sequence and reproduce the stored optimized MP4 bytes. File and recursive-folder deletion inventory **every** object before fencing reads; retry until active Cloudinary objects and Atlas records are both confirmed removed. Old v1 records continue on the old reader and download path. Migration, if offered, happens only in an unlocked browser and leaves the old object readable until the v2 replacement is fully verified.

## Acceptance before enabling v2 uploads

- Golden format vectors and tamper tests: per-object nonce/key uniqueness, index binding, missing/reordered/substituted fragments, metadata alteration, truncated ranges, strict individual and aggregate byte caps.
- Browser-local real transcode with audio/orientation preserved and MSE playback/seek tests on generated disposable media; prove nonzero seeks use bounded range reads and do not load the entire video. Verify duration, audio sync, speed, fullscreen and repeated seek after lock/reopen on supported browsers.
- Disposable Cloudinary plus Atlas integration: all objects restricted, unsigned and alternate URLs denied, actual byte counts confirmed, false/replayed completion rejected, partial transfer cancelled/reconciled, and active objects plus metadata removed by file and recursive deletion. Simulate provider/DB failures and process restart.
- Production HTTPS trials on supported desktop, Android Chrome and iOS Safari/PWA where playback support is claimed. Record device/browser/version and memory/network observations. A plan, browser or host combination without this evidence remains **BLOCKED**.

No v2 schema, upload, player, or migration is enabled by this document. The [release gates](RELEASE_GATES.md) remain blocked.

## Isolated feasibility result

`src/lib/video/fmp4-structure.ts` now strictly parses top-level initialization and fragment byte spans, requires `mvex`, `traf`, `tfhd` relative addressing, `tfdt` and `trun`, and rejects oversized/truncated structures. Three unit tests pass. `npm run video:check` additionally remuxed a small synthetic locally optimized H.264/AAC file using FFmpeg's fragmentation flags and validated the resulting structure in Chrome. This does **not** establish independent keyframes, correct fragment timestamps, MSE append/seek, segmented encryption/upload, or phone compatibility. The existing production optimizer still emits its original fast-start MP4.
